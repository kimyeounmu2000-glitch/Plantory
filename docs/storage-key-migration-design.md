# 저장 키 분리 및 명시적 이전 설계

상태: 설계 검증 후보, 실제 앱 미적용. 기준 main b0587b1. 2026-11-18.

## 경계와 키

- 기존 plantory_full_mvp_v2: 새 앱에서 읽기만 한다. 삭제·setItem·자동 복원·자동 업데이트 금지.
- 제안 plantory_full_mvp_v3: 이전 후 새 앱의 쓰기/백업/복원/스냅샷/잠금이 사용하는 단일 키. 잠금 이름은 plantory_full_mvp_v3-write.
- 이름의 v3는 저장 공간 분리를 뜻한다. 내부 JSON version:2를 이번 설계에서 임의 변경하지 않는다. 미래 멘트 필드는 별도 호환성 승인과 검증 대상이다.
- 키를 매 배포마다 바꾸지 않는다. 비호환 writer와 분리해야 할 때만 별도 이전 검토를 한다.
- 기존 legacy prototype 자동 이전 경로도 새 키에 조용히 쓰지 않도록 변경 필요. 이 설계에서는 기존 legacy 코드/데이터를 수정하지 않는다.

## 이전 절차와 상태

1. 사용자가 구버전 탭·설치 앱을 닫고 기존 JSON 백업을 별도 파일로 확보한다. 새 앱은 첫 진입에 자동 이전하거나 빈 데이터로 저장하지 않는다.
2. 새 키가 존재하면 정상/손상 여부와 무관하게 기존 키로 덮어쓰거나 재이전하지 않는다. 정상은 새 키 사용, 손상은 쓰기 차단·원문 보존/복구 안내. 새 키 읽기 오류 역시 빈 상태로 오인하지 않는다.
3. 새 키가 없으면 구 키를 읽기 전용으로 검사한다. 원문과 크기/검증 결과를 보관하고 사용자에게 옮길 기록과 비동기화 한계를 설명한다. 원문은 UI에서 HTML로 해석하지 않는다. 없음/빈 문자열/손상은 구분한다.
4. 원문의 모든 필드를 손실 없이 읽고 다시 내보낼 수 있는지 검증한다. 필터링·기본값 치환으로 잘못된 기록을 조용히 제거하지 않는다. 미지원 필드는 원문 백업을 유지하고 이전을 차단한다. 정상 celebration은 그대로 유지하고 날짜별 꽃 기록과 일치하는지 검사한다. 미확인 미래 스키마를 추정해 변환하지 않는다.
5. 명시적 이전 선택 후 새 키의 Web Lock 안에서 새 키 없음 및 확인 당시 구 원문과 동일함을 재확인한다. 변경됐으면 쓰지 않고 재확인 요구. 잠금 미지원/읽기 오류면 쓰기 금지.
6. 검증된 원문 전체를 단 한 번 setItem으로 새 키에 기록하고 같은 문자열인지 읽어 확인한다. 중간 플래그/원본 삭제/자동 동기화는 사용하지 않는다. 실패 시 원본은 그대로 남는다. 예외 후 새 키가 존재하는지 별도로 확인하고 성공/실패 상태를 모호하게 숨기지 않는다.
7. 복사 후 구 원문이 바뀌었다면 새 키를 자동 삭제하거나 다시 복사하지 않는다. 복사본을 보존하고 '원본이 변경되어 비교 필요' 상태로 쓰기를 막는다. 양쪽을 각각 백업하고 사용자가 확인하도록 한다. 이 상태는 새로고침으로 사라져선 안 된다. 영속 상태를 기록할 메타데이터 방식은 실제 구현 전에 별도 검토 필요하며 이번 프로토타입에는 구현되지 않았다.
8. 성공하면 새 키만 사용한다. 이후 구 키 변경은 새 키에 자동 반영하지 않는다. 다시 이전 버튼은 기존 새 기록을 덮어쓰는 우회로가 되면 안 된다.

## 호환성 위험 / 실제 구현의 필수 조건

- 현재 main normalize는 celebration을 제거한다. 원문 복사만 성공해도 첫 편집이나 JSON 복원 때 멘트 이력이 없어질 수 있다. 읽기/저장/export/import 전 경로의 손실 없는 검증이 필요하다. 로컬 7da6ab0의 검증기를 검토하되 멘트 기능을 임의 병합하지 않는다.
- 기존 앱 normalize의 filter/slice/기본값 보정은 가져오기에 손실을 만들 수 있다. 이전 전후 items/awards/growth/settings/celebration 비교 및 지원 불가 기록의 명시적 거절을 검증해야 한다.
- 과거 JSON은 새 버전에서 검증 후 가져올 수 있도록 하되, 복원은 현재 기록의 대체임을 확인하고 복원 전 새 키 백업을 제공한다. 멘트 필드 없는 백업을 덮어쓰면 이력이 되돌아감을 명시한다. 구 앱으로 새 JSON을 가져오면 멘트 이력이 제거될 수 있으므로 금지 안내한다.
- 구 키의 기록을 구버전 자체가 수정하는 것은 막지 못한다. 이전 전 백업과 비교를 위한 원문 snapshot이 기준이며 양쪽의 편집을 자동 병합하지 않는다.
- 구 writer는 원자적 읽기+쓰기 협약에 참여하지 않으므로 마지막 비교 직후 변경을 완전히 배제할 수 없다. 이전 전 구 탭 종료가 필요하고, 복사한 snapshot 이후 구 변경을 포함한다고 보장하지 않는다.
- 같은 origin에서 키만 나누므로 보안 경계가 아니다. localStorage.clear(), 사이트 데이터 삭제, 브라우저 축출/비공개 모드 종료, 같은 origin의 악성 코드, 저장 용량 경쟁은 양쪽에 영향을 줄 수 있다. 별도 JSON 파일 백업이 필요하다.
- 데이터 두 벌로 저장 용량이 증가한다. 용량 부족 때 원본을 지워 공간을 확보하지 않는다. 파일 백업 후 별도 대응을 사용자와 결정한다.
- 코드 롤백 시 구 키로 자동 복귀하면 이전 이후 기록이 없는 것처럼 보인다. 새 키 읽기/내보내기를 유지하는 복구 버전 또는 새 백업 확보 후 명시적 복구가 필요하다.

## 설계용 검증 범위

- tests/check-storage-migration-design.cjs는 기존 check-mixed-version-storage.cjs를 먼저 실행해 현재 앱의 실제 손실 실패를 재확인한다. 이 실패가 개선된 것으로 바꾸지 않는다.
- 실제 구 HTML e469574 + 별도 격리 HTTPS 페이지의 원문 복사 프로토타입으로 키 분리 효과를 검사한다. 실제 앱 코드에 주입하거나 적용하지 않는다.
- 테스트: 원문/할 일/일정/완료/꽃/성장/celebration 동일 복사, 구 writer 저장 후 새 키 불변, 이전 전/후 새로고침, 기존 대상 재이전 거절, 동시 탭 단일 이전, 인위적 QuotaExceededError와 재시도, 전/후 원본 변경 탐지, 손상 원본/대상 보존, 잠금 없음 실패 차단, 원문 JSON 왕복.
- 용량 검사는 브라우저 용량을 실제로 고갈시키지 않고 예외를 주입했다. 강제 프로세스 종료/OS 전원 손실/디스크 장애는 미실시. 실제 앱 백업 UI로 celebration 복원, 이전 확인 UI, 변경 충돌 상태의 재시작 보존도 미구현/미실시다.
- 앱/모델 파일 불변이므로 이번 시험을 새 앱의 CRUD·성장·3D 전체 회귀 통과로 보고하지 않는다. 실제 적용 후 모든 기존 회귀와 생성본 일치 검사가 다시 필요하다.

## 다음 승인 범위

실제 앱 키 변경, 손실 없는 호환성 검사, 이전 확인 UI, 중단/충돌 상태의 영속 보존 방식을 별도 브랜치에서 구현·검증하는 승인이 필요하다. 현재 설계 시험 통과만으로 main 반영 또는 데이터 이전 완료를 승인받은 것으로 해석하지 않는다.

## 2026-11-18 실제 구현 후보

- 승인 후 fix/storage-v3-migration에서 구현. 키 v3, 내부 JSON version 2 유지. v2 쓰기/삭제 없음.
- 중단 상태는 별도 plantory_full_mvp_v3-migration-pending 키에 확인 당시 원문으로 보존한다. pending 먼저 기록→v3 원문 복사→양쪽 원문 재확인→pending 제거 순서. 추가 용량 필요; 어느 단계에서 실패해도 v2는 그대로다. pending이 남으면 새로고침 및 이미 열린 다른 탭에서도 쓰기 차단.
- v3가 이미 있고 pending이 없으면 재이전 금지. pending과 v3/원본이 동일한 경우 사용자 확인으로 검증을 재개한다. 서로 다르면 자동 덮어쓰기/삭제하지 않는다. 실제 v3 손상은 기존 원문 다운로드와 쓰기 차단을 유지하며, 손상 기록 위에 자동 복원하지 않는다.
- normalize는 원본의 추가 최상위/항목/설정/celebration 필드를 유지한다. 지원하지 않는 알려진 필드·잘못된 날짜·중복 ID 등은 조용히 제거하지 않고 전체 읽기/가져오기를 거절한다. 멘트 UI·추첨은 추가하지 않았다.
- 저장 시 기존 성장 최대값을 낮추거나 꽃 획득 규칙을 바꾸지 않았다. 원문 이전은 바이트 동일 문자열 복사이며 기존 데이터에 없는 기본 필드는 정상 편집 시 보충될 수 있다.
- 초기 calendar_prototype_v1만 있는 환경은 자동 변환을 중단하고 원문 백업을 제공한다. v2 대상 이전과 구분하며 미지원 과거 형식을 임의 변환하지 않는다.
